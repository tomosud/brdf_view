# BRDF Explorer Web Development Rules

Rules for humans and AI assistants working in this repository.

## Responsibilities

- The user handles git commits, pushes, and GitHub Pages publication. The assistant may change code and documentation, but must not commit or push unless explicitly instructed.
- Run browser-independent checks and the production build when changing the web app or bundled assets. Leave final visual and interactive browser verification to the user unless explicitly requested.
- Keep attribution and bundled license files intact. This project is based on the Disney BRDF Explorer.

## Project Structure

- `web/`: Vite + TypeScript WebGL2 application.
- `web/src/`: application, UI, BRDF parser, shader builder, and render views.
- `web/public/`: static runtime files. Some contents are generated by the asset-copy step.
- `sample/brdf/*.brdf`: project-local analytic BRDF samples and the source of the bundled sample list.
- `assets/`: HDR environments and OBJ meshes copied into the production site.
- `docs/`: implementation and validation notes.
- `.github/workflows/pages.yml`: GitHub Pages build and deployment workflow.
- `serve_pages_local.bat`: serves a completed Pages-style build locally at `http://localhost:4173/brdf_view/`.

## Development and Verification

From `web/`:

```powershell
npm ci
npm run dev
npm run build
```

- `npm run dev` starts Vite for development.
- `npm run build` runs `prebuild` (`npm run copy-assets`), TypeScript checking (`tsc --noEmit`), and the Vite production build.
- The production build output is `web/dist/` and uses the GitHub Pages base path `/brdf_view/` by default.
- To check the built site with the same prefix as GitHub Pages, run `serve_pages_local.bat` from the repository root after `npm run build`.
- Do not add server-side runtime requirements; the deployed application must remain a static GitHub Pages site.

## Bundled Assets

- Edit project-local BRDF samples in `sample/brdf/`, not the generated copies in `web/public/brdfs/`.
- `web/scripts/copy-assets.ts` copies project-local BRDFs, environments, thumbnails, and meshes into `web/public/`, writes their manifests, and runs automatically before development/build commands.
- `web/public/brdfs/`, generated environment/mesh directories, and `web/dist/` are generated outputs. A build may update already tracked generated BRDF copies; keep those copies consistent with `sample/brdf/` when they are part of the repository history.
- BRDFs that approximate or extend a referenced model must say so in the `.brdf` header, validation documentation, and user-facing sample/display name. Do not present an approximation or project-specific extension as the original implementation.

## GitHub Pages

- `.github/workflows/pages.yml` runs on pushes to `main` and on manual dispatch.
- The workflow uses Node.js 22, runs `npm ci` and `npm run build` in `web/`, uploads `web/dist`, and deploys it with the official Pages actions.
- Before handing off changes intended for publication, run `npm run build` and confirm that the relevant files are present in `web/dist/` with `/brdf_view/` URLs.

## Workflow

- Read files as UTF-8. If Japanese text is garbled, correct the read method before editing.
- Preserve unrelated user changes in a dirty worktree.
- Prefer focused changes and verify them before moving on.
- Keep current public behavior in `README.md` and detailed BRDF accuracy/limitations in the existing files under `docs/`.
- When adding dependencies or external assets, verify that their licenses permit the intended use and document required attribution.
